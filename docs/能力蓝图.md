# Saligiare 能力蓝图

## 这份文档解决什么问题

Saligiare 不是一个把所有安全工具塞进同一个 Prompt 的“万能 Agent”。它是一套可以逐步扩展的安全研究 Agent 平台：同一个 Agent Runtime 在不同任务类型下加载不同的任务协议、能力计划、工具集合、隔离后端和评测器。

能力目标必须和授权边界一起定义。本文中的 CTF、CVE、内核、WebKit、安卓和 SRC 能力，默认只针对：

- 本人拥有或明确获准测试的系统、源码、镜像、设备和账户；
- 官方 benchmark、比赛平台提供的本地任务和容器；
- 专门搭建的训练靶场、虚拟机、模拟器和测试夹具。

不把“Agent 能提出一个利用思路”当成“漏洞已经被证明”，也不把模型输出的 `solved=true` 当成可信结果。可信结论必须由代码、测试、评测器和审计 Trace 共同支撑。

## 一、三条产品线

### 1. 竞赛线

服务普通 CTF 和安全 Agent 竞赛。重点是任务解析、侦察、工具编排、失败恢复、Flag/答案提交和可复现实验。

覆盖范围：

- Web、Pwn、Reverse、Crypto、Forensics、Misc 等普通 CTF 题型；
- TSECBENCH Local、Cybench、InterCode-CTF 等 benchmark；
- 需要开发漏洞挖掘、渗透或自动化解题 Agent 的比赛，例如腾讯云智能渗透挑战类比赛；
- 任务目录、Flag 提取、Writeup、成本、步数和时间统计。

竞赛线的关键限制：题目目标、工具、网络和 Flag 判定都由 benchmark 适配器或可信评测器定义，不能由模型自行扩展范围。

### 2. Real World CTF 与安全研究线

服务授权的漏洞复现、源码审计、漏洞挖掘和利用验证。它比竞赛线更重视版本、构建、证据链、补丁和回归测试。

覆盖范围：

- CVE 复现：0day、1day、Nday；
- kernelCTF 等内核专项靶场；
- Linux 内核漏洞挖掘与利用；
- Android 内核漏洞挖掘与利用；
- WebKit、WebCore、JavaScriptCore 漏洞挖掘与利用；
- Android App 渗透测试；
- Android App 漏洞挖掘与利用；
- 企业级 SRC 挖掘。

这里的 0day 需要精确定义：可以研究尚未公开修复或尚未公开编号的授权缺陷，但不能因为任务名称是“0day”就默认允许对公共目标进行测试。系统必须记录发现来源、授权证明、目标版本和人工批准状态。

### 3. 知识库线

服务学习、复现和长期积累。知识库不是一个可以改变权限的 Prompt 索引，而是带来源、版本和可信度的研究资料库。

每条知识至少应能关联：

- 漏洞或问题类型：CVE、CWE、内存安全、逻辑错误、权限边界等；
- 受影响产品、源码提交、版本和配置；
- 输入来源、触发路径、前置条件和最小复现步骤；
- 观察到的证据：日志、崩溃栈、测试结果、源码位置和 Trace ID；
- 利用性判断：仅可疑、可触达、可复现、可利用、已修复、待确认；
- 修复提交、补丁和回归验证；
- 来源、作者、时间、授权范围、置信度和人工审查状态；
- 脱敏后的学习说明和失败尝试。

知识库中的内容必须被当成不可信数据处理。它可以帮助 Agent 回忆，但不能自动授予 Shell、网络、设备、内核或浏览器权限。

## 二、能力不是一个开关：五种运行模式

| 模式 | 主要目标 | 典型执行后端 | 结果判定 |
| --- | --- | --- | --- |
| `ctf_solve` | 完成竞赛题、获取 Flag 或答案 | 任务容器、受限终端、浏览器夹具 | Flag/答案评测器 |
| `vuln_reproduce` | 在固定版本复现公开或授权漏洞 | 可复现构建容器、专用 VM、测试夹具 | 崩溃、行为差异、PoC 和版本证据 |
| `source_audit` | 从源码中发现并验证漏洞线索 | 只读源码工作区、静态分析、编译测试环境 | 源码证据、调用路径、测试和置信度 |
| `exploit_validate` | 在训练靶场验证利用链和影响 | 一次性 VM、内核 VM、安卓模拟器、浏览器沙箱 | 可信观测、权限变化、崩溃或靶场 Flag |
| `src_assess` | 对明确授权范围进行企业 SRC 检查 | 低速扫描器、请求代理、隔离凭证 | 范围内证据、去重结果和报告 |

模式之间不能只靠 Prompt 切换。模式必须由任务配置决定，并影响工具白名单、网络策略、凭证访问、审批等级、资源预算和评测器。

## 三、各能力的最小可交付定义

### 普通 CTF

第一版不追求覆盖全部题型，而是先建立统一协议：

```text
题目描述/附件
    -> 题型识别
    -> 能力计划
    -> 受限工具调用
    -> 证据和中间状态
    -> Flag/答案提取
    -> 可信评测
```

每种题型后续可以拥有自己的专家 Agent，但它们共享 `Task`、`Action`、`Observation`、`Result` 和 Trace 协议。

### Agent 漏洞挖掘或渗透竞赛

这类比赛不是普通 CTF 的简单加大版。Agent 需要同时具备：

- 目标建模和资产/接口侦察；
- 源码、配置、运行时行为和错误信息的关联；
- 漏洞假设、验证计划和最小化 PoC；
- 多步骤利用链编排；
- 失败恢复和上下文压缩；
- 发现记录、风险分类、复现步骤和报告生成；
- 由比赛平台或本地评测器确认结果。

核心设计是把“发现线索”和“确认漏洞”分开，避免模型仅凭一条异常响应就提交漏洞。

### CVE 复现

统一流程应支持 0day、1day 和 Nday，但每种类型的证据要求不同：

```text
漏洞资料/授权输入
    -> 固定受影响版本和修复版本
    -> 构建或恢复目标环境
    -> 生成最小复现测试
    -> 观察崩溃、错误行为或安全边界变化
    -> 对比修复版本
    -> 输出复现报告和不确定性
```

- 0day：必须有授权来源、目标版本和人工确认；不能把未知漏洞名称当作公共目标授权。
- 1day：应关联公开公告、补丁提交或可验证的版本差异。
- Nday：重点是稳定构建、版本矩阵、回归测试和补丁正确性。

Agent 可以生成测试和 PoC 草稿，但构建环境、运行权限、网络范围和最终结论由确定性代码控制。

### Linux 内核、Android 内核和 kernelCTF

这三类任务共享部分分析能力，但执行环境不能混用：

- Linux 内核源码审计：只读源码、调用图、数据流、KASAN/KCSAN/UBSAN、syzkaller 和专用构建环境；
- Android 内核：增加交叉编译、设备树、厂商补丁、模拟器或专用测试设备边界；
- kernelCTF：优先以官方镜像、虚拟机和 Flag 评测器为边界，不把 kernelCTF 的利用方式默认推广到真实设备。

建议拆成三个子 Agent：

```text
source-audit（只读分析）
    -> build-test（编译、Sanitizer、回归）
    -> exploit-validate（仅在批准的 VM/靶场验证）
```

源码读取和构建执行不应默认放在同一个高权限子 Agent 中。这样可以减少“分析输入污染构建命令”和“构建工具获得过多源码/凭证权限”的风险。

### WebKit 漏洞挖掘与利用

WebKit 需要单独的 C++/浏览器研究线，至少覆盖：

- JavaScriptCore、WebCore 和进程边界；
- 对象生命周期、引用计数、类型混淆和 IPC；
- 固定提交版本的构建、布局测试和回归用例；
- ASan、UBSan、模糊测试和崩溃去重；
- 测试页面、浏览器进程和网络访问的隔离。

WebKit 任务中的页面内容、HTTP 响应和测试样本都可能包含提示注入，必须作为不可信观察结果传给 Agent，不能直接变成系统指令。

### Android App 渗透与漏洞研究

建议先在自有 APK、公开训练 App 和离线模拟器中实现：

- APK 元数据、权限、组件和导出面分析；
- JADX/apktool 等静态分析结果的结构化导入；
- ADB、模拟器、代理和测试账号的受限调用；
- Frida/动态插桩的明确脚本白名单；
- 深链、WebView、IPC、存储、认证和网络安全配置检查；
- 从“风险线索”到“可复现漏洞”的证据链。

真实设备、真实用户数据和生产接口必须是单独的审批级别，不能因为使用了测试 APK 就自动放行。

### 企业级 SRC 挖掘

SRC 是范围和速率约束最严格的模式之一。任务必须包含：

- 明确的域名、应用、IP、接口、时间窗口和禁止测试项；
- 资产发现和请求速率上限；
- 低风险检查与高风险验证的分级；
- 凭证、Cookie 和个人数据的最小暴露；
- 人工批准点，例如越权验证、写操作、敏感数据读取和漏洞利用；
- 去重、证据脱敏、报告模板和停止开关。

默认情况下，Saligiare 不应对未列入任务范围的公共资产发起请求，也不能根据模型从网页、知识库或错误信息中推断出新的目标范围。

## 四、对核心架构的影响

能力蓝图会直接约束后续接口设计。

### `Task`

任务至少需要包含：

```text
task_id
mode
target
scope
source_version
allowed_capabilities
required_approval
budget
evaluator_id
metadata
```

`scope`、`allowed_capabilities`、`required_approval` 和 `evaluator_id` 必须由可信任务加载器注入，不能由模型修改。

### `CapabilityPlan`

Agent 不应直接从自然语言跳到任意工具。它先提出结构化计划，例如：

```text
目标：验证固定 Linux 内核版本中的授权测试用例
需要：source_read、build_test、vm_exec
禁止：宿主机写入、公共网络、未批准凭证
成功证据：崩溃栈 + 复现命令 + 版本哈希
```

Policy Guard 对计划逐项审批，并将计划编译成一次运行的工具能力集合。

### `Tool Registry` 与 `Policy Guard`

工具按能力域分组，而不是按命令字符串随意开放：

```text
source_read
static_analysis
build_test
terminal_sandbox
browser_fixture
android_emulator
kernel_vm
network_probe
report_write
```

Policy Guard 默认拒绝，至少检查：任务模式、目标范围、参数 Schema、命令/路径、网络方向、资源预算、审批状态和输出大小。

### `Sandbox`

不同任务需要不同后端：

| 后端 | 用途 | 不能假设的事情 |
| --- | --- | --- |
| 容器 | 普通 CTF、源码静态分析、构建 | 容器天然等于完整隔离 |
| 一次性 VM | 内核、漏洞利用验证 | VM 不会自动限制外部网络 |
| Android 模拟器 | APK 动态分析 | 模拟器数据自动安全脱敏 |
| 浏览器沙箱 | WebKit 测试夹具 | 页面内容可信 |
| 受限代理 | 授权 SRC 检查 | 代理自动知道任务范围 |

### `Evaluator`

评测器必须按任务模式分别实现：

- CTF：Flag/答案和任务状态；
- CVE：崩溃、行为差异、受影响版本和修复对比；
- 源码审计：证据位置、调用路径、测试和置信度；
- 利用验证：靶场内可观察影响，不接受模型自报；
- SRC：范围内证据、去重和报告完整性。

## 五、分阶段实现顺序

不要按照“能力列表”逐项堆工具，而按风险和复用程度推进：

1. `ctf_solve` + Fake Runtime：建立通用任务、动作、工具、策略和 Trace 协议。
2. TSECBENCH Local：验证 benchmark 适配器和可信评测器。
3. 普通 CTF：扩展终端、附件、浏览器和逆向工具的隔离能力。
4. `vuln_reproduce`：先做公开 Nday，再做 1day，最后在明确授权下研究 0day 流程。
5. `source_audit`：先做普通 C/C++ 项目，再进入 Linux 内核和 Android 内核。
6. `kernel_vm` 与 kernelCTF：单独建立 VM、镜像、资源限制和利用验证后端。
7. WebKit：固定提交、最小构建、测试夹具和 Sanitizer 先行，再研究漏洞利用。
8. Android App：先自有 APK 和模拟器，再加入动态插桩与复杂漏洞验证。
9. `src_assess`：最后加入严格范围、速率限制、审批和报告流水线。
10. 知识库和回归平台：贯穿以上阶段，但权限系统永远独立于知识库。

## 六、能力完成的判定

某项能力只有同时满足以下条件，才可以在 README 或实验报告中声明“已支持”：

1. 有明确的任务协议和授权范围字段。
2. 有专用工具白名单、策略测试和隔离后端。
3. 有至少一个可版本固定的本地任务或训练靶场。
4. 有成功、失败、超时、越权和提示注入测试。
5. 有可信评测器，不依赖模型自报成功。
6. 有源码/命令/版本/结果组成的审计 Trace。
7. 有脱敏后的知识库记录和复现说明。
8. 有限制条件、未覆盖场景和已知误报/漏报说明。

“能调用某个工具”只能算实验能力，不算完成了该安全能力。
