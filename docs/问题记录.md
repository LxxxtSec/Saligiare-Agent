# Saligiare 问题与解决记录

这份文档记录 Saligiare 开发过程中遇到的问题、排查过程、最终解决方案和可复用经验。
它既是故障记录，也是学习日志的一部分。

## 记录原则

1. 每个实际遇到的问题都记录，不只记录代码错误。
2. 记录事实、原因、解决步骤和经验，避免只写“已经修好”。
3. 不记录 API Key、Personal Access Token、密码、Cookie、目标凭证或其他秘密。
4. 命令可以记录，但要删除其中的敏感参数和真实路径中的隐私信息。
5. 问题解决后保留记录，不删除失败过程；失败过程有助于以后排查。
6. 每条记录使用唯一编号，方便在提交、Issue 和对话中引用。

## ISSUE-001：推送时报 `Repository not found`

### 现象

执行：

```bash
git push -u origin main
```

终端返回：

```text
remote: Repository not found.
fatal: repository 'https://github.com/LxxxtSec/Saligiare-Agent.git/' not found
```

### 排查过程

1. 检查远程地址是否写错。
2. 确认 GitHub 上是否真的存在目标仓库。
3. 确认当前账号是否有访问私有仓库的权限。
4. 注意 GitHub 对私有仓库的权限错误也可能返回这个提示。

### 原因

当时远程仓库尚未确认创建完成，且本地 GitHub 认证状态也没有确认。这个错误不能单独证明是 URL 错误，也不能单独证明是登录错误。

### 解决方法

先确认远程地址：

```bash
git remote -v
```

然后在浏览器中用目标 GitHub 账号确认仓库存在，最后使用有效的 GitHub Token 完成推送。

### 可复用经验

遇到 `Repository not found` 时，按这个顺序检查：

```text
远程 URL
→ 仓库是否存在
→ 当前账号是否有权限
→ 本地凭证是否有效
```

## ISSUE-002：本地没有 `gh` 命令

### 现象

执行：

```bash
gh auth status
```

终端返回：

```text
zsh: command not found: gh
```

### 原因

GitHub CLI 没有安装。`gh` 是可选客户端，不是 Git 推送的必要依赖。

### 解决方法

没有安装 `gh` 时，仍然可以使用普通 Git 加 HTTPS Personal Access Token 完成推送：

```bash
git push -u origin main
```

如果以后需要安装 GitHub CLI，再单独安装并执行：

```bash
gh auth status
```

### 可复用经验

区分：

- `git`：版本控制和远程推送的基础工具。
- `gh`：GitHub 的辅助命令行客户端。

缺少 `gh` 不等于 GitHub 不能使用。

## ISSUE-003：重复添加 `origin`

### 现象

执行：

```bash
git remote add origin https://github.com/LxxxtSec/Saligiare-Agent.git
```

终端返回：

```text
error: remote origin already exists.
```

### 原因

本地仓库已经存在名为 `origin` 的远程地址。`git remote add` 只能新增一个没有同名的远程。

### 正确处理

先查看：

```bash
git remote -v
```

地址错误时修改：

```bash
git remote set-url origin https://github.com/LxxxtSec/Saligiare-Agent.git
```

只有确实要删除再重建时才使用：

```bash
git remote remove origin
git remote add origin https://github.com/LxxxtSec/Saligiare-Agent.git
```

### 可复用经验

`remote add` 是“新增”，`remote set-url` 是“修改已有地址”。遇到重复添加错误时，不要重复执行 `add`。

## ISSUE-004：Git 提交身份与 GitHub 登录身份混淆

### 现象

执行：

```bash
git config user.name
```

输出了：

```text
beizishaozi
```

### 原因

`git config user.name` 只记录 commit 的作者名称，不负责 GitHub 认证。它可以和 GitHub 用户名不同，因此不能用它判断当前终端登录了哪个 GitHub 账号。

### 正确处理

为当前仓库设置提交身份：

```bash
git config --local user.name "LxxxtSec"
git config --local user.email "你的 GitHub 验证邮箱"
```

查看当前仓库配置：

```bash
git config --local --list
```

如果要修正尚未推送的最后一次提交作者：

```bash
git commit --amend --reset-author --no-edit
```

### 可复用经验

必须区分两种身份：

```text
Git commit 作者信息 != GitHub 远程认证凭证
```

## ISSUE-005：GitHub 不支持使用账户密码推送

### 现象

输入 GitHub 用户名后，在 Password 位置输入账户密码，返回：

```text
remote: Invalid username or token. Password authentication is not supported for Git operations.
fatal: Authentication failed
```

### 原因

GitHub 已经不允许使用账户登录密码进行 HTTPS Git 操作。

### 解决方法

使用 Personal Access Token 作为 Password：

```text
Username: GitHub 用户名
Password: Personal Access Token
```

Token 需要只授予目标仓库必要的 Contents 读写权限。Token 只在生成时保存到安全位置，不放进命令、文档或代码。

如果 macOS 缓存了错误凭证，可以清除 GitHub 的钥匙串凭证后重新认证：

```bash
printf "protocol=https\nhost=github.com\n\n" | git credential-osxkeychain erase
```

### 可复用经验

终端提示 `Password` 时，HTTPS Git 场景下通常应输入 Token，而不是 GitHub 登录密码。输入 Token 时终端不显示字符是正常现象。

## ISSUE-006：`.DS_Store` 成为未跟踪文件

### 现象

执行：

```bash
git status --short --branch
```

看到：

```text
## main...origin/main
?? .DS_Store
```

### 原因

macOS Finder 自动生成 `.DS_Store`，它不是项目源文件，也不应该提交到仓库。

### 解决方法

在仓库根目录的 `.gitignore` 中加入：

```gitignore
.DS_Store
```

然后提交忽略规则：

```bash
git add .gitignore
git commit -m "chore: 添加 Git 忽略规则"
git push
```

### 可复用经验

看到 `??` 时先用 `git status --short` 确认文件内容和来源，不要习惯性执行 `git add .`。

## ISSUE-007：`pyproject.toml` 的 Ruff 配置和终端行尾显示引起误判

### 现象

初次填写 `pyproject.toml` 时，Ruff 配置行写成了类似下面的形式：

```toml
target-version = ["py311"]
```

并且终端输出看起来像是行尾有一个 `%`：

```text
target-version = "py311"%
```

### 原因

`target-version` 应该是单个字符串值：

```toml
target-version = "py311"
```

终端显示的 `%` 不是文件内容，而是 zsh 在命令输出没有换行时显示的提示符。通过字节检查可以确认文件最后实际包含换行：

```bash
tail -c 40 pyproject.toml | od -An -t x1c
tail -n 4 pyproject.toml | sed -n l
```

### 解决方法

将配置调整为：

```toml
[tool.ruff]
line-length = 100
target-version = "py311"
```

使用 Python 内置的 `tomllib` 验证：

```bash
python3 -c 'import tomllib; tomllib.load(open("pyproject.toml", "rb")); print("pyproject.toml 语法正确")'
```

### 验证证据

终端输出：

```text
pyproject.toml 语法正确
```

字节检查显示文件最后一行以换行符结束，行尾没有 `%` 字符。

### 可复用经验

- 配置文件中的值类型很重要：字符串、数组和数字不能混用。
- 看到终端行尾的特殊字符时，先判断它是否来自 Shell 提示符。
- 使用解析器验证语法，使用 `sed -n l` 或字节检查验证不可见字符。

## ISSUE-008：Docker CLI 可用但 daemon 未启动

### 现象

Docker CLI 可以正常显示版本和插件信息，但 `docker info` 的 Server 部分报错：

```text
Cannot connect to the Docker daemon at unix:///Users/mac/.docker/run/docker.sock. Is the docker daemon running?
```

因此构建 Saligiare 沙箱镜像也失败：

```text
docker build -t saligiare-sandbox:test -f docker/sandbox/Dockerfile .
ERROR: Cannot connect to the Docker daemon at unix:///Users/mac/.docker/run/docker.sock. Is the docker daemon running?
```

启动 Docker Desktop 并成功构建镜像后，第一次运行 smoke test 又出现了新的错误：

```text
invalid argument "type=bind,src=...,dst=/workspace,rw" for "--mount" flag: invalid field 'rw' must be a key=value pair
```

修正挂载参数后，smoke test 又报告：

```text
docker: Error response from daemon: failed to create task for container: failed to create shim task: OCI runtime create failed: ... "/bin/printf": stat /bin/printf: no such file or directory
```

### 复现步骤

```bash
docker info
docker build -t saligiare-sandbox:test -f docker/sandbox/Dockerfile .
```

### 排查过程

1. `docker --version` 和客户端插件信息正常，说明 Docker CLI 已安装。
2. `docker info` 无法返回 Server 信息，说明当前 CLI 找不到可用的 Docker daemon。
3. `docker build` 在读取 Dockerfile 之前就失败，因此不能把第一阶段问题归因于 Dockerfile、Python 代码或镜像构建上下文。
4. daemon 启动后，smoke test 已经进入 `docker run`，错误进一步暴露为 Docker 29 对 `--mount` 参数的严格解析。
5. 挂载参数修正后，容器可以创建，但测试命令不存在于当前 Alpine 镜像。

### 原因

第一阶段原因是 Docker Desktop 的图形界面或后台 daemon 尚未运行。Docker CLI 只是客户端；真正创建镜像和容器的是 daemon。两者是独立进程，所以“CLI 已安装”不代表“容器运行环境已就绪”。

第二阶段原因是 Docker 29 的 `--mount` 解析器要求挂载选项使用键值形式，旧写法中的裸 `rw` 不再被接受。Saligiare 原先生成了：

```text
type=bind,src=<workspace>,dst=/workspace,rw
```

第三阶段原因是 `alpine:3.20` 是精简镜像，不保证提供独立路径 `/bin/printf`；镜像默认提供的是 BusyBox 多调用二进制。smoke test 已改为调用 `/bin/busybox printf hello`，避免为了测试而扩大镜像内容。

### 解决方法

在 macOS 上启动 Docker Desktop：

```bash
open -a Docker
```

等待 Docker Desktop 完全启动后重新检查：

```bash
docker info
```

只有当输出同时包含完整的 `Client` 和 `Server` 信息时，才继续构建镜像：

```bash
docker build -t saligiare-sandbox:test -f docker/sandbox/Dockerfile .
```

镜像构建成功后，运行显式开启的 Docker smoke test：

```bash
SALIGIARE_DOCKER_SMOKE=1 \
SALIGIARE_SANDBOX_IMAGE=saligiare-sandbox:test \
python -m pytest tests/sandbox/test_docker_smoke.py -q
```

代码已将挂载参数改为 Docker 29 兼容的显式形式：

```text
type=bind,source=<workspace>,target=/workspace,readonly=false
```

smoke test 使用镜像内置命令：

```text
/bin/busybox printf hello
```

### 验证证据

最终验证已完成：Docker daemon 正常运行，挂载参数修正后的真实 Docker smoke test 通过，输出为 `1 passed`。项目全量测试也通过（`73 passed, 1 skipped`），因此本问题标记为“已解决”。

本次验证证据：

- `docker info` 成功返回 Server 信息；
- `docker build` 成功生成 `saligiare-sandbox:test`；
- smoke test 输出 `1 passed`；
- Ruff 检查和 `git diff --check` 通过。

### 可复用经验

- 先区分 Docker 客户端、Docker Desktop 和 Docker daemon，避免把环境启动问题误判为项目代码问题。
- `docker info` 是判断 daemon 是否可用的首选命令；只看 `docker --version` 不足以证明容器环境可运行。
- 依赖 Docker 的测试应通过环境变量显式开启，并在 CI 或本地日志中记录镜像标签，保证测试对象明确。

## ISSUE-009：当前环境无法解析 TSECBENCH 官方页面和搜索引擎

### 现象

Phase 6 需要核对 TSECBENCH Local 的官方任务字段和生命周期，但 `open-websearch` 在当前环境无法取得官方页面：

```text
fetch-web: Request URL could not be resolved
search: getaddrinfo ENOTFOUND cn.bing.com
```

### 复现步骤

```bash
open-websearch fetch-web \
  'https://tsecbench.zc.tencent.com/benchmark/prepare/4?mode=local#top' \
  --readability --max-chars 20000 --spawn --json

open-websearch search \
  'TSECBENCH local benchmark prepare mode local official' \
  --limit 5 --engine bing --spawn --json
```

### 排查过程

1. `open-websearch --help` 正常，说明本地 CLI 已安装。
2. `fetch-web` 和 `search` 都进入了检索流程，但外部 URL/DNS 解析失败。
3. 这不是 Saligiare 适配器的 Schema 或测试失败，不能通过修改 Python 代码解决。

### 原因

当前运行环境没有可用的官方站点解析或外网 DNS 路径，具体是网络环境问题，尚未确认是代理、DNS 或目标站点限制。

### 解决方法

先不修改核心 Agent，也不把自定义本地夹具字段宣称为官方协议。随后通过浏览器成功加载官方页面，并根据页面内容增加独立的官方协议模型和 Fake Client 生命周期测试。自定义本地夹具仍与官方协议分层保存。

### 验证证据

- `open-websearch --help` 成功；
- `open-websearch fetch-web` 和 Bing 搜索曾因当前网络解析失败；
- 浏览器成功加载官方页面；
- 官方页面确认了 Python SDK、VPN 前置、`list_challenges/start_challenge/submit_flag/close_challenge` 生命周期和数据类字段；
- 本地 TSECBENCH 适配器和全量测试此前通过（`95 passed, 1 skipped`）。

### 可复用经验

- 不能把“官方页面暂时不可访问”当成协议不存在，更不能用自定义字段冒充官方字段。
- 先区分工具安装、daemon 状态、网络连接、DNS/代理和目标站点响应。
- 外部协议未验证前，把不确定性隔离在适配器层，核心运行时保持稳定。

## ISSUE-010：TSECBENCH Token 被粘贴到聊天中

### 现象

用户在对话中提供了 TSECBENCH 访问 Token 和 Base URL，Token 因此已经离开本机凭证存储边界。

### 风险

Token 属于可用于访问 benchmark 评测接口的敏感凭证。即使当前没有执行任何提交 flag 或启动题目操作，也不能继续把该 Token 当作安全凭证使用。

### 处理方法

1. 立即在 TSECBENCH 平台撤销或轮换已暴露 Token。
2. 在本机终端设置新 Token，不要再次粘贴到聊天、Issue、日志或 Git 文件中。
3. Base URL 可以写入本地 `.env`，但 Token 仍应由本机秘密管理工具或未跟踪的环境文件提供。

示例（值只在本机输入）：

```bash
export BENCHMARK_TOKEN='平台重新生成的 Token'
export BENCHMARK_BASE_URL='https://tsecbench.zc.tencent.com'
```

### 当前状态

当前不使用聊天中暴露的 Token，也没有发起 TSECBENCH API 请求。等待用户完成 Token 轮换后再进行只读连通性检查。
